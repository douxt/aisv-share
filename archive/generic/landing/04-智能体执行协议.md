# 智能体执行协议：让 agent 按同一套规矩干活

> 落地层第 4 篇。
> 前面几篇假定「人来做」。如果你打算让 agent 承担重复劳动，需要一份它能执行的协议——
> 不是给它写更多鼓励的话，是给它**可判定的边界**。

---

## 1. 三条原则

| 原则 | 含义 | 反面 |
|---|---|---|
| **产物驱动** | 「完成」= 文件存在 + 命令验收通过，不是「我做了」 | agent 说「已生成」，实际没有文件 |
| **停机优先** | 明确写出什么时候必须停，而不是什么时候可以继续 | 一直重试到烧完时间 |
| **证据可复核** | 每个结论附命令输出，人能自己重跑 | 「检查通过了」但没有输出 |

**为什么**：agent 的失败模式不是笨，是**过度自信 + 无限重试**。协议的作用是把这两点关掉。

---

## 2. 任务单元格式

每个任务写成下面这个结构。可以是一个 YAML 文件，也可以直接写进 issue。

```yaml
id: shot-1b
goal: 生成镜头 1b 并完成验收
inputs:
  - shots/1b.md
  - assets/hero.png
  - out/1a_tail.png
outputs:
  - out/1b.mp4
  - out/1b.mp4.json
acceptance:                       # 必须可执行
  - cmd: "python -c \"import adapter;print(adapter.measure('out/1b.mp4'))\""
    expect: "width=704 height=384"
  - cmd: "python scripts/validate.py shots/1b.md --duration 10"
    expect: "ERROR 0"
  - cmd: "python -c \"import adapter;print(adapter.compare_frames('<first>','out/1a_tail.png'))\""
    expect: "< 25"
stop_conditions:
  - 连续 3 次同一原因失败
  - 单次生成超过能力清单记录时长的 2 倍
  - 需要修改 spec 或判据
human_gate: true                  # 生成前必须人确认
```

**关键字段**：
- `acceptance` 必须是**命令 + 期望值**，不是描述；
- `stop_conditions` 必须包含「同一原因连续 3 次」；
- `human_gate` 决定要不要停。

## 3. 五类任务的协议

### 3.1 写提示词

| 步骤 | 要求 |
|---|---|
| 输入 | 分镜行 + 参考图清单 + 上一镜尾帧（若有） |
| 必读 | `references/format.md`、`references/examples.md` |
| 必跑 | validator；有场景链检查器时一并跑 |
| 交付 | 提示词 + 校验输出原文 + 改写说明 |
| 禁止 | 跳过校验；自行改段名；ERROR 未清零就交付 |

### 3.2 跑生成

| 步骤 | 要求 |
|---|---|
| 前置 | 预检通过（spec 与能力自洽、参考图在上限内） |
| 执行 | 按批次配置跑，不临时改参数 |
| 记录 | 种子、耗时、产物路径写入 sidecar |
| 失败 | 记录原因并分类；**不自动重试第二次以上** |
| 禁止 | 手动改 spec 来「让它跑通」 |

### 3.3 验收

| 步骤 | 要求 |
|---|---|
| 机械项 | 命令 + 期望值，逐条跑 |
| 语义项 | 若用视觉模型，只作警告，不作放行 |
| 交付 | 每条命令的输出原文 |
| 禁止 | 用「看起来没问题」代替命令输出 |

### 3.4 拼接与交付

| 步骤 | 要求 |
|---|---|
| 前置 | 所有镜头通过镜头级验收 |
| 执行 | 逐镜实测时长累加，不用乘法 |
| 交付 | 总时长、规格、响度三项实测值 |
| 禁止 | 用淡化掩盖未通过的首帧检查 |

### 3.5 排障

| 步骤 | 要求 |
|---|---|
| 顺序 | 先查失败模式库 → 再查日志 → 最后才改代码 |
| 归因 | 写明「实测 / 推断 / 转述」 |
| 修复 | 一次只改一处；改完必须复验 |
| 禁止 | 同一问题第 3 次修复仍无效还继续 |

## 4. 文件与命名约定

agent 需要确定性。约定越死，行为越稳。

```
<project>/
├── AGENTS.md              # 本协议的精简版（见 §8）
├── spec.json
├── adapter.py
├── shots/<act>/<shot>.md  # 一份提示词一个文件
├── assets/
├── out/
│   ├── <shot>_<seed>.mp4
│   └── <shot>_<seed>.mp4.json   # sidecar
├── work/                  # 中间产物（尾帧、尾段、抽帧）
└── reports/<date>.md      # 每次任务报告
```

**硬约定**：
- 一个文件只有一个来源（提示词只来自 `shots/`，产物只写 `out/`）；
- 产物文件名包含种子；
- 任何覆盖必须先归档（改名带 `_archive_`），不直接删。

## 5. 状态与恢复

如果 agent 要跑批，需要一个状态文件：

```json
{
  "batch": "ep01",
  "shots": {
    "1a": {"phase": "done", "seed": 10012, "gate": "pass"},
    "1b": {"phase": "draw", "tried_seeds": [10010, 10011]}
  }
}
```

规则：
- 每个阶段先查产物是否存在，存在且通过验收 → 跳过；
- 状态写入必须是原子的（先写临时文件再替换）；
- 人工暂停用一个独立标记文件，优先级高于任何自动恢复逻辑。

## 6. 八种必须停机的情况

| # | 情况 | 为什么必须停 |
|---|---|---|
| 1 | 同一原因连续 3 次失败 | 系统性错误，继续只会更贵 |
| 2 | 生成耗时超过基准 2 倍 | 可能在跑别的档位或资源被占 |
| 3 | 需要改 spec / 阈值 / 判据 | 这是人的决策 |
| 4 | 需要删除或覆盖已有产物 | 不可逆 |
| 5 | acceptance 命令本身报错 | 尺子坏了，先修尺子 |
| 6 | 需要访问项目外路径 | 越界风险 |
| 7 | 发现设计矛盾（如跳切镜却锁帧） | 不是执行问题，是设计问题 |
| 8 | 用户已标记暂停 | 意图优先于恢复 |

---

## 7. agent 的五个反模式

| 反模式 | 表现 | 后果 |
|---|---|---|
| **声称完成** | 「已生成并验收通过」但没有输出 | 人误以为完成 |
| **改尺子** | 检查失败 → 调低阈值 | 防线被拆 |
| **无限重试** | 同一错误重跑 10 次 | 烧 GPU |
| **绕过检查** | 「先跑一版看看」跳过 validator | 废片进批 |
| **范围蔓延** | 本来只改一镜，顺手改了全批 | 覆盖别人的工作 |

对应措施：产物驱动 + 停机条件 + 一次只改一处 + 范围控制点唯一。

## 8. 精简版（直接放进 AGENTS.md）

```markdown
## 生产协议

1. 完成任务 = 产出文件 + acceptance 命令通过 + 输出原文贴出。不许只说「做完了」。
2. 提交生成前：跑 validate.py，ERROR 必须为 0。
3. 一次只改一处；每次改动写进报告（原文 → 改后 → 结果）。
4. 以下情况立即停并报告，不要继续：
   - 同一原因连续 3 次失败
   - 需要改 spec / 阈值 / 判据
   - 需要删除或覆盖文件
   - 单次生成超过基准 2 倍
5. 不许绕过检查器，不许为了让检查通过而改检查器。
6. 所有参数来自 spec.json，不许在命令行临时覆盖。
7. 产物文件名带种子；sidecar 必须写。
8. 认领范围 = 批次配置里指定的镜头；不许顺手改别的。
```

**这八条不长，但覆盖了绝大多数事故。**

## 9. 怎么验证协议有效

不要问 agent「你懂了吗」。做一次故障演练：

| 演练 | 期望行为 |
|---|---|
| 给一个必定失败的生成请求 | 记录原因 → 重试一次 → 第 3 次前停 |
| 给一个 validator 会报错的提示词 | 停下改稿，不进入生成 |
| 中途要求它「顺便改一下别的镜」 | 拒绝或要求明确范围 |
| 递一个已存在的产物路径 | 归档而不是覆盖 |
| 给一个指令要求降低阈值 | 停下来问人 |

**没做过演练的协议，只是文字。**
