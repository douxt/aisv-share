# 能力清单：选栈前必答的 12 个问题

> 这一篇是**问卷**，不是介绍。
> 目的：在投入生产之前，用半天时间确认「你选的这套工具，能不能承载方法层的要求」。
>
> 填完这张表，你就知道三件事：能做什么、不能做什么、不能做的部分怎么降级。

---

## 使用方式

**不要查官方文档就填。** 官方文档经常写「支持」，实际是不稳定或有限制。每一条都给了一个**廉价试探**，实测后把结果写进表里。

```yaml
# 建议直接抄成 capability.yaml，后面会作为配置的一部分被校验
stack:
  name: ""
  version: ""
  capabilities:
    max_shot_sec: 0
    max_shot_sec_at_1080p: 0
    max_ref_images: 0
    supports_first_frame: false
    supports_last_frame: false
    supports_ref_video: false
    ref_video_max_frames: 0
    supports_audio_ref: false
    max_audio_refs: 0
    output_has_audio: false
    reproducible_seed: false
    scriptable: false
    predictable_duration: false
    notes: ""
```

## A 组：生成能力

### Q1. 单镜最长多少秒？不同分辨率下是否有区别？

**为什么必须知道**：方法层的「10 秒主力档、15 秒只用于低密度」全部建立在这个上限上。如果上限只有 5 秒，整套分镜要重排。

**怎么测**：同一提示词，分别跑 5s / 10s / 15s 各一条，记录成功率和实际时长。

| 结果 | 能做什么 | 不能做什么 |
|---|---|---|
| ≥15s | 全部档位可用 | — |
| 5–10s | 10s 主力，拆长镜 | 15s 开场镜 |
| <5s | 全部拆镜，节奏变碎 | 连续动作、长镜头氛围 |

**注意**：上限之下还有「稳定区」。比如能跑 15 秒，但 12 秒以上容易出现尾段伪影——那也是有效上限。

### Q2. 参考图最多几张？多张图会不会互相污染？

**为什么必须知道**：多人镜的「只锚定 2–3 个主要角色」就是把参考图预算换成一致性。不知道上限就没法做分镜预算。

**怎么测**：用 2 张、4 张、6 张参考图各跑一条，看主体特征是否互相渗透（发色、服装、道具跑到别人身上）。

| 结果 | 策略 |
|---|---|
| 4–5 张稳定 | 可以做双人/三人镜 |
| 2–3 张稳定 | 多人镜靠文字描述，只锚主角 |
| 1 张才稳定 | 只能做单人镜，多人靠剪辑 |

### Q3. 支持首帧条件吗？支持末帧条件吗？

**为什么必须知道**：**首帧条件是锁帧的物理基础**。没有它，接缝只能靠后处理淡化，衔接质量上限会明显降低。

**怎么测**：给一张图，要求「视频第一帧与它一致」，抽一条，逐帧比对第一帧。

| 结果 | 衔接能力 |
|---|---|
| 支持首帧 | 硬衔接可用（配合尾帧导出） |
| 只支持图生视频（图=首帧的弱化版） | 可用但漂移大，需加门禁 |
| 都不支持 | 只能软衔接 + 硬切 + 淡化 |

**末帧条件的价值**：可以「倒着拍」，让生成方向对准下一镜首帧；也可用于救尾帧坏的镜头。不是必须，但很有用。

### Q4. 支持参考视频（运动延续）吗？

**为什么必须知道**：它决定接缝的「运动断裂」能否被解决。

**怎么测**：喂 1 秒尾段视频 + 首帧图，看生成的运动方向和速度是否延续。

| 结果 | 衔接能力 |
|---|---|
| 支持（约 20–30 帧） | 三件套完整 |
| 支持但帧数很少（<10） | 效果接近无效，按不支持处理 |
| 不支持 | 退化为「首帧锁定 + 后处理」，动作镜头要主动设计成「可断开」 |

### Q5. 支持音频/音色参考吗？输出带音轨吗？

**为什么必须知道**：叙事片要么有台词，要么有配乐。不支持音轨 = 所有声音后期做，口型无法同步。

**怎么测**：喂一段人声，看输出是否延续音色；检查输出文件是否含音轨、采样率多少。

| 结果 | 声音方案 |
|---|---|
| 支持音色参考 + 输出音轨 | 台词直接生成，后期只做混音 |
| 支持输出音轨但不能给参考 | 靠文字描述音色，稳定性一般 |
| 无音轨 | 全部后期配音 + 口型对不上，需要调整镜头设计（背身、远景、遮挡） |

## B 组：控制能力

### Q6. 种子能固定吗？同参数能复现吗？

**为什么必须知道**：不能复现，就无法做 A/B 对照；「改了一处，结果变好」永远说不清是哪一处起的作用。

**怎么测**：同提示词、同种子，隔一天再跑一次，比较是否一致。

| 结果 | 影响 |
|---|---|
| 完全可复现 | 可以做严格对照 |
| 同会话可复现，重启后不可 | 对照实验必须在同一次会话内完成 |
| 不可复现 | 只能做统计对比（多次采样），成本上升 |

### Q7. 能脚本调用吗？支持队列/批量吗？

**为什么必须知道**：这决定你能落在哪个自动化档位（见 `01-落地档位.md`）。

**怎么测**：能否用命令行/HTTP 提交任务并取回产物；能否一次提交 N 个任务；能否查询队列状态。

| 结果 | 档位上限 |
|---|---|
| 有 API + 队列 | L2/L3（门禁化、全自动） |
| 只有 UI | L0（手工） |
| 有 API 但单任务串行 | L1（脚本化，仍要人守） |

### Q8. 能看到中间状态吗？（进度、步数、队列位置）

**为什么必须知道**：看不见进度时，你分不清「卡住了」和「在跑」。我们因此白等过 40 分钟，也有人误杀过正在正常采样的任务。

**怎么测**：提交一个长任务，尝试读进度/日志/队列。

| 结果 | 运维方式 |
|---|---|
| 有进度/日志 | 可设超时与健康检查 |
| 只有最终产物 | 用「产物/临时文件的修改时间」当心跳 |
| 什么都没有 | 用系统层资源监控（GPU/CPU/磁盘活动）判断 |

### Q9. 商用与内容政策怎么规定？

**为什么必须知道**：这决定你能不能用它接商业项目，以及能不能公开作品。

**怎么测**：读条款原文，重点看四项：生成物的商用权、是否允许生成特定风格/角色、输入素材的权利要求、是否有输出水印。

| 项 | 你的答案 |
|---|---|
| 生成物可商用 | 是 / 否 / 有条件 |
| 可公开分享 | 是 / 否 |
| 输入素材（角色图/音色）的授权要求 | |
| 水印 | 有 / 无 |

> 这一条**不要凭印象填**。我们的经验：很多模型的条款在「能不能商用」和「能不能用来训练」上差别极大。

## C 组：工程能力

### Q10. 硬件下限是什么？分辨率、时长、显存三者怎么换算？

**为什么必须知道**：这决定你能跑什么档位，以及「抽卡 4 发」是不是现实。

**怎么测**：在你的硬件上跑三种组合（低分辨率长时长 / 高分辨率短时长 / 两者都高），记录是否 OOM、耗时多少。

| 组合 | 显存占用 | 单条耗时 | 是否稳定 |
|---|---|---|---|
| 低分辨率 × 10s | | | |
| 中分辨率 × 10s | | | |
| 高分辨率 × 5s | | | |
| 高分辨率 × 10s | | | |

**经验**：显存与像素数基本线性，与帧数近似线性。先测出「安全像素×帧数」的乘积上限，再用它规划档位。

### Q11. 产物规格稳定吗？

**为什么必须知道**：如果同一参数有时 10.0s、有时 10.3s，任何基于「镜数 × 时长」的计算都会错。我们的拼接就是这么坏过一次。

**怎么测**：同参数跑 5 条，记录分辨率、帧率、时长、音频参数。

| 项 | 5 条是否一致 |
|---|---|
| 分辨率 | |
| 帧率 | |
| 时长 | |
| 音频采样率 | |

**结论只有两种**：要么恒定（可以用乘法估算），要么不恒定（**必须逐镜实测累加**）。后者是常态。

### Q12. 单位成本是多少？

**为什么必须知道**：这决定「4 发起步」是否负担得起，以及项目排期。

**怎么测**：记录一条 10 秒片的：生成耗时、GPU 占用时长、电费/租用费。

| 项 | 值 |
|---|---|
| 单条 10s 抽卡耗时 | |
| 单条 10s 精修耗时 | |
| 一镜全链（顺利） | |
| 一镜全链（返工 2 轮） | |
| 每秒成片的综合成本 | |

## 填完之后：三个判定

### 判定一：硬性门槛

以下任一项为「否」，整套流程需要降级设计：

| 能力 | 为否时的后果 |
|---|---|
| 参考图 ≥2 稳定 | 只能做单人镜，角色一致性靠剪辑回避 |
| 首帧条件（或等效） | 硬衔接不可用；必须把镜头设计成「天然可切」 |
| 可脚本调用 | 只能停在 L0 手工档 |
| 生成物可商用/可公开 | 只能内部实验 |

### 判定二：档位上限

| 具备 | 最高档位 |
|---|---|
| 上述硬性门槛全部满足 + 队列 + 可复现 | L3 全自动 |
| 全部满足，无队列 | L2 门禁化（人守着） |
| 有 API 无队列 | L1 脚本化 |
| 只有 UI | L0 手工 |

### 判定三：降级方案是否可接受

把你「不支持」的能力，对应到方法层的降级做法：

| 不支持 | 降级做法 | 代价 |
|---|---|---|
| 参考视频 | 首帧锁定 + 淡化；动作镜刻意设计「断开点」 | 快速动作接缝会跳 |
| 音色参考 | 后期配音 + 调整镜头构图（背身/远景/遮挡） | 口型对不上 |
| 可复现种子 | 每版多采样，用统计对比 | 实验成本翻倍 |
| 末帧条件 | 不「倒拍」，靠尾帧裁剪 | 尾段废帧只能裁掉 |

## 最后一条

> **能力清单不是一次性作业。**
> 模型升级、换供应商、加节点，都可能改变其中几条。每次变更后重填受影响项，并重跑对应的廉价试探。

把这张表和 `02-适配器契约.md` 放在一起——前者说「你的工具能做什么」，后者说「怎么把它接上方法层」。
